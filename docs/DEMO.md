# Що показувати під час доповіді — 10 слайдів, 15 хвилин

Мета показу: одна зміна коду проходить автоматичну перевірку та потрапляє на опублікований сайт. Усі дії основного показу виконуємо у браузері GitHub. Налаштовувати проєкт або встановлювати npm перед аудиторією не потрібно.

## Відкрити заздалегідь

- [Опублікований сайт](https://maryangemini.github.io/devops-demo/).
- [Workflow](https://github.com/maryangemini/devops-demo/blob/main/.github/workflows/deploy.yml).
- [Функція Stop](https://github.com/maryangemini/devops-demo/blob/main/src/camera.js) і [перший тест](https://github.com/maryangemini/devops-demo/blob/main/test/camera.test.js).
- [Редактор VERSION](https://github.com/maryangemini/devops-demo/edit/main/src/main.js).
- [Actions](https://github.com/maryangemini/devops-demo/actions).
- [Чернетковий PR №1](https://github.com/maryangemini/devops-demo/pull/1) з назвою **Demo: failed Stop test — do not merge**. Для швидкого показу відкрий [невдалий запуск](https://github.com/maryangemini/devops-demo/actions/runs/38593617284/job/115954568367) → Run tests.

## План за слайдами

| Слайд | Час | Що показати | Основна теза |
| --- | --- | --- | --- |
| 1. GitHub Actions | 0:30 | Слайд; коротко сайт із камерою | На цьому проєкті покажу перевірку та автоматичну публікацію зміни. |
| 2. Навіщо автоматизація | 1:00 | Слайд | Після кожної зміни повторюємо однакові перевірки; workflow виконує їх автоматично. |
| 3. CI та CD | 1:00 | Слайд | CI перевіряє й збирає; CD доставляє результат. Тут deployment автоматичний після успіху CI. |
| 4. Workflow | 1:00 | Верх `deploy.yml`: `on`, `jobs`, `runs-on` | YAML описує процес; push у main запускає його; runner виконує команди. |
| 5. Кроки CI | 1:30 | `steps` від checkout до build; за потреби `package.json` | Отримали код, підготували Node, встановили залежності, запустили тести, створили dist/. |
| 6. Що перевіряє тест | 1:00 | Перша функція в `src/camera.js`, перший тест у `test/camera.test.js` | Після Stop очікуємо `video.srcObject === null`. Тест написали ми, Node запускає його. |
| 7. Що буде при помилці | 1:00 | Заготовлений невдалий запуск PR: Run tests червоний, build/deploy пропущені | Тест знайшов реальний дефект. Помилкова гілка не змінила опублікований сайт. |
| 8. Публікація | 1:00 | Низ `deploy.yml`: artifact, `needs: build`, deploy-pages | Готові файли передаються через artifact; Pages публікує їх після успішного CI. |
| 9. Живий показ | 5:00 | VERSION → commit у main → новий Actions run → оновлений сайт | Зміна коду автоматично потрапила на хостинг за тією самою адресою. |
| 10. Висновок і питання | 2:00 | Оновлений сайт, потім слайд | GitHub Actions повторює заданий процес, показує результат перевірок і автоматизує публікацію. |

Час включає переходи між вкладками. Питання аудиторії: «Чи опублікується зміна, якщо тест завершиться помилкою?»

## Слайд 6 — тест, який легко пояснити

У `src/camera.js` покажи тільки першу функцію. Вона зупиняє tracks і виконує:

```js
video.srcObject = null;
```

У першому тесті покажи дві дії:

```js
stopCamera(video);
assert.equal(video.srcObject, null);
```

Фраза: «Ми викликаємо нашу функцію та порівнюємо результат з очікуваним. npm test запускає написані нами тести через Node.js». Тести використовують mock stream; вони не відкривають фізичну камеру на runner.

## Слайд 7 — заготовлений невдалий запуск

У чернетковому PR `demo/failing-test` закоментовано лише очищення `video.srcObject` у stopCamera. Відкрий **Files changed**, покажи цей рядок; потім **Checks** або пов'язаний запуск у Actions.

Покажи:

1. `Run tests` — failure; назву першого тесту і повідомлення порівняння.
2. `Build website` — skipped.
3. `Deploy to GitHub Pages` — skipped.

Фраза: «Тест очікує null, а відео зберегло посилання на потік. Перевірка зупинила процес до збірки». Для PR публікація також заборонена умовою `if`, навіть коли тести успішні. При помилці тесту в main залежність `needs: build` теж не дозволила б deployment.

Це демонстраційний PR: **не натискай Merge**. Не кажи, що GitHub автоматично заборонив злиття: для такої заборони потрібні окремі правила гілки; тут вони не налаштовані.

## Слайд 9 — головний показ деплою змін

### 1. До зміни — 30 секунд

Відкрий сайт та покажи **Version 3.0**. На початку або після оновлення коротко увімкни камеру, покажи рамку навколо обличчя та Stop.

Скажи: «Це вже опублікований сайт. Зараз зміню його код у GitHub і покажу, як оновлення потрапить на хостинг».

### 2. Зміна й commit — 45 секунд

У [редакторі src/main.js](https://github.com/maryangemini/devops-demo/edit/main/src/main.js) зміни тільки:

```js
const VERSION = '3.0';
```

на:

```js
const VERSION = '3.1';
```

Натисни **Commit changes**. Повідомлення: `Demo: publish Version 3.1`. Обери commit безпосередньо у **main**. Commit через GitHub створює зміну в репозиторії та подію push, тож термінал не потрібний.

Якщо сайт уже має 3.1 після репетиції, використай 3.2 або інше наступне значення. Зміна номера доводить доставку файлів; нової функції сама по собі вона не додає.

### 3. Автоматичний запуск — приблизно 2–3 хвилини

Відкрий [Actions](https://github.com/maryangemini/devops-demo/actions), знайди запуск із повідомленням свого commit. Покажи його commit SHA — це конкретна версія коду, яку перевіряє запуск.

Відкрий job **Test and build**, покажи `Run tests` і `Build website`. Поки він працює, поясни: «Я більше не запускаю команди вручну: їх виконує runner». Потім покажи **Deploy to GitHub Pages**. Дочекайся **success** обох jobs. Під час очікування можна повернутися до слайду 8 та відповісти на питання; тривалість запуску залежить від черги GitHub і мережі.

### 4. Результат — 45 секунд

Онови ту саму адресу сайту. Має з'явитися **Version 3.1**. За потреби виконай Ctrl+F5. Якщо CDN ще віддає старі файли, зачекай трохи та онови повторно.

Скажи: «Зміна пройшла перевірку, готові файли опублікувалися на GitHub Pages, і користувач отримав нову версію за тією самою адресою».

Це справжнє розгортання статичного сайту на хостингу GitHub Pages. Тут немає власного VPS, SSH або серверного backend. Runner і хостинг — різні середовища.

## Перед виступом

- Перевір авторизацію GitHub, камеру, дозволи та інтернет на тому самому ПК.
- Завчасно відкрий невдалий запуск; його не треба запускати наживо.
- Переконайся, що останній запуск main успішний та сайт доступний.
- Зроби власний короткий запис успішного переходу VERSION як запасний варіант; при показі запису прямо скажи, що це запис репетиції.
- Репетируй один раз із таймером. Не витрачай виступ на npm install, термінал чи налаштування Pages.
